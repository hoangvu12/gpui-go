# Windows scene renderer contract

Status: selected by [Choose the scene renderer and GPU backend](../.scratch/gpui-core/issues/07-choose-scene-renderer.md), 2026-10-04. This is a design selection under the user's research-first delegation, not a working renderer or GPU validation result. It extends the [Windows host](windows-platform-contract.md) and [runtime ownership](runtime-ownership-contract.md) contracts.

## Architecture

Extract the pinned CE **Direct3D 11 renderer, DirectComposition integration, scene kernel, atlas and shader tooling** into a maintainer-built native service. Load prebuilt Windows AMD64 artifacts from Go with `CGO_ENABLED=0`. Go owns the application, entities, elements, layout, paint traversal, frame/cache scopes and HWND loop. The service owns no second GPUI application or entity runtime.

The native scene kernel includes the value types, bounds/order tree, layer operations, primitive insertion and replay, sorting, batching, filter planning and GPU packing needed by the renderer. Reusing only `Scene::finish` would leave ordering and replay compatibility to a new Go implementation. Preserve the complete finite data-processing kernel instead. This is an explicit extension of the renderer service boundary; it does not move Go element callbacks or retained application state into Rust.

| Responsibility | Owner |
|---|---|
| Paint traversal, masks/transforms/style inputs, deferred draw scheduling, cache eligibility | Go GPUI core |
| Ordered semantic paint commands and resource leases | Go frame construction; copied into native staging |
| Bounds-based draw order, layer stack, order-floor changes, scene replay/finish/plan | Pinned native scene kernel |
| GPU record packing, pipelines, shaders, path targets, filters, atlas and surface views | Native renderer |
| Font selection/shaping/CPU raster pixels | Selected text service; Go coordinates raster requests and renderer uploads |
| HWND lifetime, foreground dispatch and wake delivery | Go Windows host |
| D3D11 device/context, swap chain, DirectComposition objects, submission retirement | Native service on the owning foreground thread |
| Vsync waiting | One host-owned pacing worker; no second native app loop |

The source is CE `254b5dbd47cbb5acbcc5bbdcbb322a339276c88a`. See the [renderer snapshots](../evidence/renderer/manifest.json), [scene](../evidence/core/crates__gpui__src__scene.rs), [plan](../evidence/core/crates__gpui__src__scene__plan.rs), [GPU layout metadata](../evidence/core/crates__gpui__src__scene__abi.rs) and [reviewed research](../research/17-scene-renderer-strategy.md). The [PC inventory](../evidence/windows-target-inspection.json) identifies the initial target; no graphics feature or driver test was run.

## Why this backend

The pinned Windows host constructs D3D11 and DirectComposition. Its device selection enumerates adapters and requests feature levels 11.1/11.0 with BGRA support. Preserve the reference enumeration and report the actual selected adapter/feature level; the RTX 5050 inventory does not prove selection or successful initialization. Failure to create a supported device is explicit. Do not silently introduce WARP, Vulkan or D3D12 fallback.

The pinned wgpu implementation is a credible alternate backend, with locked wgpu 29.0.4 and a Windows D3D11-to-D3D12 capture-sharing path plus CPU-upload fallback. Its optional custom-GPU/surface features are separate from backend selection. Choosing it would add backend-equivalence and interop work relative to the native Windows reference. A wgpu-native bridge would add another ABI adaptation. Neither is the baseline for this decision.

A pure-Go GPU renderer could consume precompiled shader artifacts and need not compile shaders at runtime. It would still require porting the reference's pipelines, packing, composition, atlas and recovery behavior. Prefer the native extraction to concentrate new work in the service seam. No comparative speed, memory, disk or build-size claim has been measured. No ready-made bridge or artifact has been verified.

## Scene construction and replay

Go records ordered commands for starting/ending layers, changing the deferred-draw order floor, inserting every primitive class and replaying a retained scene range. Primitive records carry the corresponding bounds, masks, colors, gradients, corner/border data, transforms and resource references. Native insertion computes reference draw orders from the bounds tree and layer state. Do not replace this with arbitrary sorting of independently collected arrays or a single painter-order counter.

Scene finishing preserves the pin's per-type stable ordering, sprite order/tile tie-breaks, surface-opacity pairing and filter-boundary ties. Empty clipped ordinary primitives may disappear; matching filter boundaries must survive clipping. Deferred draws raise the order floor so overlays and their backdrops remain above earlier groups. Preserve path geometry conversion, stroke/dash/wavy-underline behavior and the source's draw-limit checks.

The selected filter planner isolates at most two nested groups. Deeper groups render inline exactly as the pinned plan directs; they do not acquire an invented third isolation target. Group opacity is not implemented as independent child alpha, and backdrop filtering samples the already rendered target, not an unrelated image. Preserve matched boundaries, target-stack transitions, rounded masks, smoothing, blur downsampling/ping-pong passes and offscreen-target requirements.

Native scenes and replay ranges are explicit owned handles. A replay reference pins the old scene and its logical resource dependencies while native code copies/reinserts the selected operations. It is independent of the old GPU submission's retirement. Cached Go views retain callbacks, state and dependencies under the runtime contract; cached native scene operations alone are insufficient. Stale range/generation errors fail before publication. Abandoning a new packet preserves the previous published CPU artifacts, but does not roll back application mutations or claim that a partially submitted GPU frame is transactional.

## Pixels, atlas and shaders

Keep native atlas allocation and GPU tile mapping. Go stores generation-checked logical image/glyph resource handles; a raw `AtlasTile` layout or recycled texture index is not a durable cross-language identity. Retained scenes pin logical resources through replay, and submissions pin physical resources through last GPU use. Cache release and submission completion are separate prerequisites for tile reuse/removal. Device generation changes invalidate all physical tiles, even if a logical font/image resource remains alive.

Preserve the pinned atlas upload validation before allocation/publication, texture limits, and separate monochrome/subpixel/polychrome pools. Monochrome uses R8_UNORM; subpixel and polychrome use BGRA8_UNORM with different pixel meanings. The text service's AlphaMask, BgraSubpixelMask and BgraColor outputs stay tagged through packing and blending. Preserve gamma, grayscale/subpixel contrast and RGB/BGR order uniforms, dual-source subpixel behavior, color-glyph interpretation and transformation/sampling rules. Preblend and premultiplication must follow each pipeline; one blanket alpha conversion is not valid for the whole scene.

Go obtains raster bytes before calling the atlas insertion seam. Native atlas code may not call an arbitrary Go builder while holding its mutex. It validates/copies bytes into owned staging and publishes a tile only after a successful upload path. CPU upload bytes can be released after the native copy/consumption acknowledgment; GPU resources remain held through completion. Cache keys include the exact face/axes/synthesis, glyph, size, scale, prepared raster style, subpixel variant and relevant font/settings generation. Image/SVG resource identity and atlas removal behavior remain part of the same coverage inventory.

The renderer uses BGRA8_UNORM targets, the pinned path intermediate/MSAA setup and pipeline blend states. Retain the source's four-sample path configuration and validate it on the target device; a source comment is not hardware proof. Preserve straight-alpha scene geometry versus premultiplied path/compositor handling, filter intermediates and surface opacity. No HDR or alternate color-space behavior is selected here.

Maintainers build the shader artifacts from the pinned `gpui_render` Rust-authored shader sources through wgsl-rs, WGSL validation/translation and the Naga toolchain. Record wgsl-rs revision `b2de16a1b81e67d76bc265c296184f882864badb`, Naga 29.0.4 and legacy Naga 24.0.0, including the legacy HLSL lowering. On Windows the build invokes `D3DCompile` for `vs_5_0`/`ps_5_0`, yielding DXBC embedded in the artifact. Consumer app builds and renderer startup do not run this shader toolchain. Record generated-code/layout manifests, compiler flags and shader hashes, not only source version labels. The complete target dependency/features and native-import list remain distribution build evidence; related locks include etagere 0.2.15 and windows 0.62.2, with 0.61.3 in capture interop.

## Surface import and capability reporting

The inspected native renderer accepts `SurfaceSource::WindowsCapture`, retains the frame's D3D11 texture, creates a shader-resource view and binds the RGBA capture view to the shader's plane slots. It preserves masks and separately sorted surface opacity. Other sources take an explicit unsupported-source path. The wgpu-specific `ExternalSurface` error and sharing/fallback implementation are not automatically the native renderer's behavior.

Expose capture frames through native-owned, generation-checked handles, with COM ownership and producer-readiness obligations. Validate source kind, dimensions, format, sample/mip/array layout and device compatibility before rendering. COM reference ownership keeps an object alive; it does not itself synchronize a producer overwriting its pixels. Preserve/review the capture producer's frame-buffer contract and hold producer/frame resources until the relevant copy or GPU read is finished.

A direct D3D11 SRV path is not general cross-device sharing. Do not reinterpret a pointer from another device, invent a keyed-mutex protocol, or import the wgpu CPU fallback silently. Same-device and cross-device capture cases are mandatory gates. If a required reference capture case fails, diagnose the reference and adapter, and record any confirmed upstream limitation under the parity policy before claiming coverage. Enumerate the full Windows build's source variants and optional capabilities in conformance/distribution; unsupported native variants must be explicit, not represented by blank successful draws. This decision does not declare every optional upstream backend/feature combination implemented.

For the framework-owned capture producer, select a same-device native adapter: wrap the renderer's DXGI device as a WinRT Direct3D device, create the capture frame pool from it, and preserve BGRA8 capture settings, dimensions and timestamps. The wrapper API accepts an existing DXGI device, and the free-threaded pool accepts the supplied WinRT device and raises frame arrivals on its worker. This is a selected bridge adaptation, not a claim about the pin's `windows_capture` device setup. [Device wrapper](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.directx.direct3d11.interop/nf-windows-graphics-directx-direct3d11-interop-createdirect3d11devicefromdxgidevice), [frame-pool API](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded?view=winrt-26100).

Obtain that `IDXGIDevice` by querying the renderer's `ID3D11Device`, with an explicit failure path. Do not use the pin's optional `DirectXRendererDevices.dxgi_device` member: it is absent when DirectComposition is disabled. Capture device setup must work independently of the selected composition mode.

Retain the native capture-frame object, not merely its texture pointer, until its data has been copied into service-owned texture storage. The arrival worker posts a coalescible notification; foreground native work checks out frames and owns them through copy completion. Application callbacks and immediate-context copies run through the selected dispatcher. Serialize context access and audit the capture API's concurrent device use. Use the same-context copy/draw order and a completion marker covering the copy before returning the source frame to its pool. Published capture handles own immutable destination content through all later draws, with bounded queue/backpressure and explicit discard cleanup. Capture-pool resize/device loss closes or recreates the producer after old-frame obligations settle. This keeps buffer recycling out of the app's lease semantics. Cross-device external handles remain unsupported unless a separately specified synchronization/copy adapter is added; they are not silently accepted by this path. The complete producer path remains unimplemented and must be checked against the reference capture API and real Windows behavior.

Capture frames are short-lived native processing resources, never retained application snapshots. Copy only the valid content rectangle within the pool surface, and return/dispose each source frame after its copy retires; unused surface area can be undefined. Prefer coalesced arrival notifications and foreground frame checkout over an unbounded queue of checked-out frames. Set and verify immediate-context multithread protection before giving the shared device to capture, while retaining foreground serialization of framework commands; its return value reports the previous setting, not success/failure. These choices still require concurrency/resize tests. [Capture frame lifecycle and content bounds](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [multithread protection](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_4/nf-d3d11_4-id3d11multithread-setmultithreadprotected).

## Window surfaces, pacing and reentry

The native service receives a leased HWND, logical window generation, resize generation, scale and device-pixel extent. Match the pinned triple-buffer flip-sequential swap chain: DirectComposition uses premultiplied alpha, while the HWND route uses ignored alpha. Preserve the reference DirectComposition-disable mode; host window styles and renderer creation mode must agree. Native code owns its swap chain and composition resources; Go owns `DestroyWindow`.

Submit from a safe foreground boundary after application updates release exclusive access. D3D11 immediate-context calls, atlas uploads, resize and teardown are serialized there. Nested paint requests are deferred/coalesced, not recursively rendered into shared context state. No native registry/atlas lock is held across Go callbacks or potentially reentrant host operations. `Present(0, 0)` remains a submission/presentation result, not completion evidence. Surface/GPU failures invalidate or request reconstruction without erasing the host's window identity.

Use one host pacing worker based on the pinned DWM wait/interval behavior, including its fallback when occluded/asleep output makes waits return too early. It posts coalescible redraw opportunities; it never accesses Go entities or the immediate context. Modal move/resize progress remains the host's responsibility. Completion polling continues even when redraws are suspended for minimized/hidden windows. Do not busy-spin on a nonready query or hold the UI thread waiting for a GPU fence.

Bound in-flight native submissions and pending visual work. Apply backpressure before accepting more GPU work and coalesce only redundant redraw requests; logical events, effects and terminal retirement records are not droppable frames. The concrete capacity is an internal tuning value to validate for responsiveness, not permission for an unbounded queue or a new benchmark gate.

On resize, stop accepting stale-extent submissions, retain dependencies for work already accepted, and resize at a safe point. Release/unbind all direct and indirect back-buffer references before `ResizeBuffers`, then reacquire the new buffers and update the native generation. Recreate dependent path/filter targets as needed. Zero-sized/minimized composition surfaces are suspended rather than passed invalid dimensions. This follows the [DXGI resize requirements](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-resizebuffers).

## Completion and failure protocol

The inspected DirectX renderer has no explicit per-submission query/fence retirement protocol. Add one at the service seam; do not call it preserved source behavior. A successful submit acknowledgment means native staging owns the accepted packet and resource references. It does not release the submission scope. Returns before acceptance leave ownership with Go; errors after partial GPU work still return/retain a trackable submission token for eventual retirement.

Use `D3D11_QUERY_EVENT` as the baseline completion primitive. End a query after the last GPU command using the protected resources, including copies and auxiliary uploads. Poll `GetData` on the immediate context and accept completion only when it returns `S_OK` with a true result; `S_FALSE` remains pending. Queries can cover a group of ordered submissions if the acknowledgment mapping is explicit. Reuse query objects only after their previous result has retired. See [event query semantics](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_query) and [GetData](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-getdata).

Ensure the marker has actually been submitted before relying on `DONOTFLUSH` polling. In particular, when rendering goes idle, a window hides or shutdown drains, explicitly flush pending commands once as needed; do not infer marker submission from an earlier Present. Polls remain bounded and yield to the host. A flush is asynchronous and is not an acknowledgment. [DONOTFLUSH caveat](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_async_getdata_flag), [Flush semantics](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush).

Every accepted submission has exactly one terminal record: completed, rejected-before-use, or aborted after native-confirmed loss/teardown made further access impossible. Cancellation after submission only prevents normal result delivery; it cannot free GPU dependencies. A query error, timeout, Present error or device-generation change is not by itself a safe-abort proof. Stop the old queue, detach/release bindings and imported-resource ownership under the documented device-loss path, and acknowledge only after the native service can establish safe retirement. If that cannot be established, quarantine old-generation dependencies and keep the service loaded; report failure without pretending it completed. Tests must exercise this exceptional path before release.

Device loss invalidates old native handles, atlas mappings and cached GPU state. Recreate device/pipelines/targets/atlas/composition, request fresh rendering and preserve the pin's skipped-draw transition. Stale frame packets are rejected and logical resources can be reuploaded into the new generation. Recoveries and retry delays must be scheduled without sleeping inside a live app update; this scheduling is a Go-host adaptation of the pin's bounded recovery retries.

Cached native scenes containing old physical atlas tiles are invalidated too. Mark the corresponding Go paint caches for reconstruction while preserving their live application/element state and input dependencies; replay must not reuse stale texture indices after device recreation.

Close first rejects new work, then drains completed or safely aborted submissions and detaches the renderer before HWND destruction. Shared device resources survive other independent windows. Native code must remain loaded for every scene/resource/import/query/callback lease, not just the last HWND. The [distribution contract](distribution-contract.md) selects the stricter initial policy of process-lifetime DLL residency with no hot unload. Normal shutdown continues processing terminal records after app delivery scopes close; it cannot guarantee cleanup after OS process termination.

## Private ABI

Use a private versioned record protocol with explicit sizes, tags, counts, offsets, integer widths and float bits. Commands reference primitive records and logical resource handles; native planning determines batch ranges and isolation targets. Rust `repr(C)`, Go struct layout, Rust vectors/enums and COM pointers are not a wire format. Native code translates validated records into its own pinned CPU/GPU structures.

Validate the entire packet before committing a new scene: overflow-safe sizes/offsets/counts, supported command/primitive tags, balanced layers/filter boundaries, valid replay ranges, resource kinds/generations, upload lengths/stride, draw limits and zeroed reserved fields. Do not sanitize coordinates/colors by changing valid reference behavior. Malformed input returns a descriptive error without publishing a half-built scene or leaking resources. GPU ABI verification compares sizes, alignment, field offsets, signedness, array stride and generated shader layouts; default Go bool/enum layout is never assumed compatible.

Native staging owns all asynchronously used bytes and handles. Synchronous borrowed buffers remain alive through the call; asynchronous code stores no raw Go pointers. Completion delivery uses copied records and fixed trampolines/generation tokens or a polled native queue, not per-object callbacks. Contain Rust panics within unwind-enabled exports and Go panics at callbacks; no foreign unwind. Exactly-once retirement covers error and panic paths as well as success.

## Required evidence

Use an independent pinned Rust scene/renderer oracle, not the extracted code as both producer and oracle. Compare semantic paint streams, computed orders, replay, sorted arrays, opacity pairing, batch boundaries, plan commands and requirements before image comparisons. Cover clipped/empty filters, ties, non-overlapping content, deferred overlays, nested depths 0–3+, cache reuse/removal, oversized and malformed packets.

On the recorded PC, compare all primitive/pipeline classes, path AA, glyph formats and subpixel settings, translucent overlaps, gradients/borders/shadows, group versus child opacity, backdrop capture, imported capture frames and presentation alpha modes under controlled fonts/DPI. The approximate visual target does not replace exact deterministic plan checks. Verify resize/minimize/restore, multiple windows, modal reentry, occlusion, monitor sleep and live frame production without stuttering.

Exercise acceptance versus completion, delayed queries, upload-only work, hidden-window retirement, cancellation, partial-submit errors, stale generations, forced device loss, capture producer reuse and shutdown. Validate actual device/format support and a clean Go-only consumer build/load/callback path. Distribution owns artifact grouping, integrity/loading policy, compiler/import dependencies and the exact feature manifest. No listed test or native build has run; no parity result is claimed.
