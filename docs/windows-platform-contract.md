# Windows platform, text and input contract

Status: selected by the [Windows decision](../.scratch/gpui-core/issues/06-choose-windows-platform-and-text.md), 2026-10-04, under the user's research-first engineering delegation. This is a design contract, not an implemented host, native artifact or parity result. It complements [ownership](runtime-ownership-contract.md) and [layout](layout-contract.md).

## Selected boundary

The subsequent [renderer contract](renderer-contract.md) now selects D3D11/DirectComposition and the finite native scene kernel. It supplies the concrete GPU retirement and same-device capture adaptation for the seam defined here; it does not introduce a second app runtime.

Use a Go-owned Win32 host and foreground dispatcher, with maintainer-built native services for the pinned Parley text implementation, Windows glyph rasterizer, AccessKit Windows provider and COM-heavy platform adapters. Consumers use Go and prebuilt DLLs with `CGO_ENABLED=0`. No second Rust GPUI application, entity store, element tree or event loop is introduced. The renderer is selected separately.

This splits by responsibility rather than language purity. Go owns GPUI behavior; native services retain algorithms and OS integrations whose replacement would add substantial parity risk. Port the selected CE Windows behavior, not an unrelated toolkit's widget model. Gio hosting is not selected: adapting its input/text/window ownership would add a second compatibility layer without removing the Parley/AccessKit work. Bridging the entire existing CE Windows platform unchanged is also not selected: its construction includes renderer/device responsibilities that must remain at an explicit seam.

| Responsibility | Owner and boundary |
|---|---|
| App/entities/effects, windows' logical scopes, focus/action routing, layout and inline orchestration | Go core, under the existing foreground and lease contracts |
| HWND creation, window procedure, message pump, geometry/DPI, keyboard/mouse/IMM32 dispatch | Internal Go Win32 host, fixed callback trampolines and generation-stamped window tokens |
| Font catalog, fallback, shaping, paragraph layout, text geometry and CPU glyph pixels | Native text service adapted from pinned `gpui_ce_parley` and Windows rasterizer; explicit font/layout/buffer handles |
| Accessibility semantics, identities and requested actions | Go builds updates; native AccessKit owns the published provider tree and COM objects |
| OLE drop targets/data objects, Direct Manipulation and native dialogs | Narrow native adapters, owned by the foreground apartment/window scope; copied messages and explicit completion |
| Clipboard item semantics and format choice | Go compatibility layer; Win32/native helpers own OS allocations and conversions as needed |
| GPU device, surface, atlas, upload, composition and presentation | Renderer decision; receives a leased HWND and typed raster data |

The [distribution contract](distribution-contract.md) combines the logical services in one exact prebuilt DLL without changing these ownership boundaries. Service code remains resident for the process lifetime; logical resources still retire explicitly. All relevant pinned platform capabilities, including dialogs, cursor/window controls and system settings, remain in the parity inventory even when they do not require a separate public Go API.

This requires a new extraction/bridge, not an already verified Go binding. Maintainers must track every adaptation to the pinned Rust text/platform code and keep an independent unmodified-reference oracle. Shared value types inside a native service are allowed; embedding the Rust GPUI runtime to obtain them is outside this boundary.

## Thread, loop and window lifetime

Start the host on a locked Go OS thread. Initialize OLE there before HWND/COM services and balance successful initialization, including `S_FALSE`, with `OleUninitialize` after all apartment-owned services retire. An incompatible existing COM apartment is an initialization error. Do not initialize COM in DLL entry points. This follows [OleInitialize](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-oleinitialize); UI Automation *client* MTA advice does not change the host's STA.

Preserve accelerator/translation/dispatch ordering and distinguish app quit from one window's destruction. A close request can be vetoed; destroying one window retires its scope and sends a generation-checked removal, without destroying independent windows or shared entities. The host owns HWND destruction; the renderer owns its surface resources. Closing rejects new submissions, invalidates logical window callbacks and drains/aborts existing native work before physical resources disappear. Nested callbacks keep active-call pins even after logical closure.

Use posted wake messages and a foreground runnable queue. No worker directly accesses entities or retained element state. Frame requests can coalesce, but input/effects preserve their contract. The host must continue safe foreground work and paint opportunities in Windows' modal move/resize and dialog loops; a top-level `GetMessage` loop alone is insufficient. Renderer pacing feeds request/completion signals into this loop; the platform does not choose a GPU backend or duplicate its vsync ownership.

Native messages cannot all be queued indiscriminately. At a safe foreground entry, key/input/close callbacks execute synchronously when their return value controls Windows handling. Synchronous native queries use current host state or an immutable published snapshot. A nested window procedure must not reacquire a live exclusive Go update or hold a registry mutex across application callbacks. Potentially pumping operations such as dialogs and drag/drop start after the current update unwinds. Reentrant queries use their documented snapshot/default response; reentrant mutating input is copied and delivered at the next safe entry. Each such message needs an explicit consumed/default-result policy in the implementation's dispatch table, compared with CE traces; there is no generic “queue everything and return zero” rule. Modal/reentry behavior is an execution gate, not yet-proved equivalence.

In particular, a close request received during an exclusive update is consumed and retried through a generation-checked foreground close decision; it must not accidentally bypass the application's veto through default processing. `WM_GETOBJECT` uses the native provider immediately, and nonclient hit-testing uses published window-control geometry. Ordinary orderly shutdown drains owned resources; OS session termination remains best effort, as in the pinned Windows handler, and cannot promise cleanup after process termination.

## Text service

Keep the lockfile versions: Parley 0.11.1, Fontique 0.11.1, HarfRust 0.12.0, Skrifa 0.44.0 and Swash 0.2.10. Preserve the pinned GPUI adapter, complex-script/system-font configuration, dependency graph and target features in maintainer build provenance. `ParleyTextSystem` loads system fonts, defaults to Segoe UI and configures Lilex, IBM Plex Sans and Arial fallback families. Installed fonts can differ; required comparison fixtures record the exact font bytes/face/axes and available system fallback environment.

Parley and its GPUI adapter own shaping, script/bidi behavior, font selection, features/ligatures, variable axes, runs, wrapping/clamping, paragraph splitting and caret/selection/hit-test geometry. DirectWrite is the selected Windows **rasterizer**, not a replacement shaping engine. The native service accepts the exact selected font face/instance and exposes the full `PlatformTextSystem`/`PlatformTextLayout` capabilities, not just glyph positions. Preserve byte-indexed text clusters and movement operations separately from UTF-16 input offsets. Paragraph-level direction and newline handling must follow the pinned adapter rather than flattening a document into one Parley layout.

Go retains GPUI style resolution, text cache keys, measurement requests, inline element traversal/placement and layout rounding. Native layout records retain text/font dependencies until explicit release. Inline atomic boxes cross as numeric records; arbitrary Go element callbacks never move into the native text service. Known dimensions, definite/min/max-content queries, runs, wrap width, line clamp, alignment, baseline, fragments and font generation remain inputs/outputs of the existing layout contract. Font additions and generation changes invalidate affected cached layouts and glyph identities; handle reuse cannot revive stale cache entries.

The Windows rasterizer attempts DirectWrite and falls back to Swash if initialization fails. Per-glyph fallback occurs for the typed unsupported cases, including variable axes on older DirectWrite, bitmap color and COLRv1; other raster failures remain errors. Do not infer complete COLRv1 support from that fallback enum: the pinned capability predicate must also be preserved and tested. Prepared raster style follows the actual backend. Preserve AlphaMask, BgraSubpixelMask and BgraColor as distinct formats, including bounds, stride, scale, subpixel variant and exact pixel interpretation. OS text-rendering settings participate in cache invalidation. GPU atlas allocation and blending remain renderer responsibilities.

## Keyboard, focus, IME and coordinates

Go routes physical/translated keystrokes through GPUI focus, key contexts and action propagation. Preserve repeat state, scan codes, modifiers, dead keys, layout-dependent characters and `prefer_character_input` behavior. AltGr-like character entry must not accidentally become a Ctrl+Alt shortcut. `WM_CHAR` is text input, not another keydown; preserve pending UTF-16 surrogate assembly and filtering behavior. Preserve the pin's accelerator pre-dispatch: a consumed key bypasses `TranslateMessage` and normal dispatch, preventing a handled shortcut from also inserting text. System-key/default processing must remain distinguishable from ordinary text. Mouse capture/release, extra buttons, multi-clicks, wheel units and Direct Manipulation precision-touchpad phases are separate platform input paths.

The inspected pin uses IMM32 (`WM_IME_STARTCOMPOSITION`, `WM_IME_COMPOSITION`, `ImmGetCompositionStringW`, composition/candidate positioning). Select that path for parity; do not claim a TSF text-store implementation. Preserve result-string replacement followed by composition/mark update when both are present, composition cursor selection, zero-lparam composition handling and the input handler's cursor-position preference. Consume the handled native messages as CE does; do not add a heuristic that drops the next arbitrary `WM_CHAR` to hide duplicate text. Commit/cancel/focus-loss traces must prove single delivery, mark cleanup and correct replacement ranges.

Maintain a generation-checked active input handler per window. Its UTF-16 selection, marked range, text-range adjustment, replacement, marked replacement, unmark, point lookup, bounds and text-length operations remain distinct from UTF-8 layout byte indices. Never cut a surrogate pair or grapheme by confusing these units. When disabling IME, preserve the pin's focused-HWND guard before completing composition: Windows can share the IME context across windows on the thread.

Use explicitly named coordinate spaces at every boundary: window-local logical bounds, client device pixels, and screen device pixels. Convert exactly once using the current window scale and origin; candidate placement must track scroll, moved windows and DPI changes. There is a source discrepancy to resolve with an oracle fixture: the core `bounds_for_range` comment says screen coordinates, while Windows `retrieve_caret_position` multiplies the returned bounds by scale without a screen-to-client translation. Do not infer the conversion from the comment alone or silently add an offset. The Windows-facing caret snapshot is window-relative, as required by the [composition](https://learn.microsoft.com/en-us/windows/win32/api/imm/ns-imm-compositionform) and [candidate](https://learn.microsoft.com/en-us/windows/win32/api/imm/ns-imm-candidateform) forms; the GPUI handler adapter must be tested against actual reference behavior at a nonzero window origin.

Use PerMonitorV2 awareness established before creating windows, matching the pinned manifest. Apply `WM_DPICHANGED`'s suggested rectangle with the new scale, and invalidate geometry, text/raster state and surface dimensions together. Renderer sizes use device pixels; app layout uses logical pixels. Packaging must ensure the application manifest/initialization requirement actually reaches consumer executables. See [WM_DPICHANGED](https://learn.microsoft.com/en-us/windows/win32/hidpi/wm-dpichanged).

## Clipboard, drag/drop and accessibility

Preserve clipboard entry types and the pinned conversions: UTF-16 text, GPUI metadata/hash association, file lists, registered image formats and DIB handling. Do not downgrade the interface to plain text. OS-owned clipboard allocations transfer on successful publication; failures release allocations locally. Read buffers are copied before unlock/close. OLE drag/drop effects and synchronous replies use native adapter state and the last published eligibility snapshot; app mutations arrive through safe foreground dispatch. Revoke drop registration, stop Direct Manipulation and release COM interfaces on the owning apartment before its shutdown.

Pin AccessKit 0.24.1 and `accesskit_windows` 0.33.1. Go builds semantic updates and stable node identities; the native adapter maintains its provider tree. Keep node identity stable while the element identity persists, and prevent a removed node/window generation from targeting a replacement. Focus and bounds update with the published semantic tree.

Follow the pinned activation pattern: return a minimal valid root immediately, post a refresh, then publish the complete update. Provider queries read the native published tree and must not call arbitrary Go state or wait for a busy UI thread. Accessibility actions enqueue copied requests with window/node generations for foreground validation. Release adapter/update locks before raising UIA events: the pinned Windows implementation explicitly does so because raising events can synchronously trigger `WM_GETOBJECT`. Provider and outstanding COM reference lifetimes can outlast logical window removal; stale requests return the appropriate unavailable result without dereferencing released app state. Validate actual locked-library behavior on RPC threads; this document does not establish it by inference from client-threading guidance.

## Native ABI and renderer seam

Use the layout bridge's versioned C-compatible records, explicit errors, fixed trampolines and generation tokens. Native code never stores raw Go object pointers; copied buffers or explicitly owned native allocations cross asynchronous boundaries. Synchronous borrowed input buffers remain alive through the call. Every native object, result buffer, callback registration and COM reference has an explicit release path; GC is not a protocol. Go panics are caught at trampolines, and Rust panics are contained inside unwind-enabled exports, never across a foreign stack. Failure retires the operation before ordinary Go error/panic propagation. DLL unload waits for all calls, provider references and owned objects, not only window closure.

Foreign-thread notifications enter a native queue and post a wake to the host; they do not invoke entity callbacks. Queue records own their payload through foreground delivery or discard. Synchronous foreground trampolines have separate active-call ownership and cannot acquire a global lock held by their caller. Library-local serialization for text state must likewise exclude callback cycles.

The renderer receives a window token, leased HWND, device-pixel extent, scale, visibility/occlusion state and resize generation. It reports frame readiness, present/device failures and terminal resource retirement to the foreground dispatcher. It may not destroy HWNDs or access entities from a driver callback. Text service outputs include font/glyph identity, raster style, bounds and typed CPU pixels; their ownership lasts through upload/copy completion. Device loss invalidates GPU resources without changing logical text or window identity. Surface creation, rendering API, color/blend behavior, atlas keys, fencing and pacing mechanisms belong to the next decision.

## Required execution evidence

Compare against an independent pinned CE application on the same PC. Record fonts, keyboard layouts, IMEs, DPI, OS text settings and driver versions. Required cases include:

- Multiple windows, veto/close/reopen, HWND/token reuse, app quit, nested dialogs, drag/drop and live resize while tasks complete; no cross-window release or deadlock.
- Latin ligatures, combining marks, Arabic/Indic, mixed-direction paragraphs/newlines, emoji/color/variable fonts, fallback and newly added fonts; measurement, wrap/clamp, inline boxes, caret movement, selections and hit tests.
- Physical keys versus characters, repeats, dead keys, AltGr, surrogate input; Japanese/Chinese/Korean composition, commit/cancel and focus transfer; no duplicate text, stale marks or shifted candidate window.
- Scroll/capture/touchpad, clipboard multi-entry formats/metadata, DPI transition at nonzero window origins, minimize/restore and surface resizing.
- Screen-reader activation before the first full tree, concurrent provider queries, text/selection actions, event-triggered reentry, node deletion and window close with outstanding COM references.
- Native load/call/free, callback panic, stale handles, cancellation and shutdown; clean Go-only consumer compilation and execution with no Rust/C toolchain.

Behavioral/text geometry checks remain distinct from the visual-closeness metric. No tests, compiler probes, native builds, installations or benchmarks were performed for this decision. The blocked Go upgrade is not retried. Bridge feasibility, detailed message policies, the coordinate discrepancy and full platform capability coverage remain explicit implementation/conformance gates; none is evidence that parity has passed.
