## Answer

- **Range from the layout record (no native change).** The native `GpuiGoLayoutRecord` already carries Taffy's `content_size`, `scrollbar_size`, resolved padding and borders (`reference/native/src/layout.rs:1690-1706`, mirrored at `internal/native/layout.go` `LayoutRecord`), so the range is computed Go-side: `LayoutEngine.ScrollLayoutFacts` (`gpui/layout.go:1038-1108`) reads the record and applies Taffy's own `Layout::scroll_width/scroll_height` formula (taffy 0.13 `tree/layout.rs:331-348`: the content size less the padding box, plus the scrollbar reservation, floored at zero) **plus the in-flow children's trailing margins** (`scrollTrailingMargins`, `gpui/layout.go:1110-1160`) — margins are recorded per node at request time (`nodeMargins`, `gpui/layout.go:701-704`) and resolved with the negative-end clamp; Taffy's content size stops at the child border boxes where Chromium's inflow bounds carry the end margins (`box_fragment_builder.cc:321-357`).
- **Content size semantics.** Taffy's content size already includes the descendants' visible overflow (recursively, `compute/common/content_size.rs:16-36`) and the container's END padding (`compute/block.rs:701-707`, `compute/flexbox.rs:2231-2236` — the comment: "The container's own padding at the end of the content is part of its scrollable overflow region"), which is the same rule Chromium's `ScrollableOverflowCalculator::Result` applies (`scrollable_overflow_calculator.cc:100-118`).
- **The clamp consumes the record range.** `elementScroll.clamp` (`gpui/scroll_element.go:149-191`) takes the caller-computed max; the div's prepaint queries the facts (`gpui/div.go:1794-1836`), keeping the tracked handle's child bounds (`trackChildBounds`); the hidden-sticky arm and the sticky scope use the same facts; the standalone inline path keeps its own extent with the record's padding (`inlineScrollMaxOf`); the uniform list keeps its virtualized extent with the record's padding (`gpui/list.go:269-300`, the frame state now carries its `layoutID`).
- **Padding percentages against the containing block's width.** The resolved padding comes from the layout record (`ScrollLayoutFacts.Padding`, `ResolvedPadding`, `gpui/layout.go:1162-1193`): Taffy resolves all four edges' percentages against the containing block's inline size (`compute/leaf.rs:19-21`: "both horizontal and vertical percentage padding/borders are resolved against the container's inline size", `compute/flexbox.rs:446-447`), so the Go side stops re-resolving vertical padding against the scroller's own height (Chromium: `LayoutBoxModelObject::ComputedPaddingOutsets`, `layout_box_model_object.cc:838-859`). `stickyScrollContextOf` (`gpui/sticky.go:113-145`) takes the resolved padding; custom scrollers (`WithStickyScrollContainer`) keep the style-side resolution (no node to read).
- **Border widths floored.** Chromium's computed border width is an integer of CSS px — `ClampLineWidth` (`style_builder_converter.cc:1971-1987`: `0 < w < 1` → 1, else `floor`), consumed as integers by the layout (`length_utils.cc:1478-1485`). The port: `clampLineWidth`/`clampLineWidthToDevice` (`gpui/layout.go:117-160`) floors the CSS px and scales it to device px UNROUNDED in the record (`gpui/layout.go:378-401`) — a 1px border at 175% lays out at exactly 1 CSS px — and the paint floors then stroke-snaps (`snapBorderWidths`, `gpui/paint.go:432-451`: the hard-edged strip needs a whole device thickness; rounding is the nearest hard approximation of Chrome's antialiased stroke). The style-side geometry that must agree with the layout (the overflow mask, content box, sticky scrollport, scrollbar tracks, list padded bounds, the inset-shadow edge) resolves through `Style.borderEdges` (`gpui/style.go:1479-1492`).
- **Note on the ticket's phrasing.** "Floored to device pixels" (and report 05 §9's arithmetic, "Blink floors 1.75 device px to 1") misreads where Chromium's floor applies: `ClampLineWidth` floors the ZOOMED/CSS pixel value, never the device value. Measured against Chrome 155 (`--force-device-scale-factor 1.75`): a 1px border insets `getBoundingClientRect` by exactly 1 CSS px and paints an antialiased 1.75-device-px strip; a 0.5px hairline at 100% insets and paints 1 CSS px. The implemented rule is Chromium's actual one — the boxes match Chrome at every scale; the residual divergence at fractional scales is the port's own bounds edge snapping (the child of a 1px border at 175% reports 2 device px = 1.1429 CSS px, not Chrome's 1.0).
- **Fixtures** (package `internal/parity/fixtures/scrollrange`, registered in `internal/parity/replay_test.go` and `cmd/parityrecord/main.go`): `scrollrange` (nested overflowing content + a 40px trailing bottom margin + a 10% top padding + a 24px end padding, scrolled to the end with the End key — Tier A exact, Tier C 0.0000 mean); `border-floor` (1.3px at the default scale: Chrome's floor gives the 1-CSS-px inset where the pin's rounding gave 1.5 — pixel-exact); `border-175` (1px at a 1.75 scale via the new `Fixture.Scale`: Tier A exact on the border box, Tier C whole-image mean 0.0709 from the hard strip vs the AA stroke); `border-hairline` (0.5px at a 1.0 scale, pixel-exact). The harness gained `Fixture.Scale` (the recorder forces Chrome's device scale, the replay opens `gpui.NewTestWindowAtScale`) and the `parity.Script` step (ticket 46's trigger; documented in `docs/browser-parity-harness.md`).
- **Tests.** Unit: `gpui/pixel_rounding_test.go` (the floor rule, the record translation, the paint snap); engine-level: `internal/layoutspec/scroll_facts_test.go` (the content size 338, the range 78, the 64px percentage padding, the 1.3px→1px inset); discrimination: `TestWrongPaddingBasisFailsTheBoxComparison` (the pre-ticket pin's own-height basis fails Tier A on every content box). The range half is gated by the record itself: a regression to the element-tree union lands every scrolled box off (the old formula gives 4, not 78).
- **Changed expectation (divergence toward Chrome, recorded):** `gpui/layout_test.go` `TestStyleToRecordBorderStrokeMinimum` → `TestStyleToRecordBorderFloor` (1.6px at scale 1: the pin rounded to 2 device px; Chrome's floor is 1) — the only existing expectation the ticket moved; no bit-exact fixture changed.
- **Key citations** (%TEMP%esearch-src\chromium): `core/css/resolver/style_builder_converter.cc:1971-1987` (ClampLineWidth), `core/layout/length_utils.cc:1478-1485` (integer borders in layout), `core/layout/scrollable_overflow_calculator.cc:100-118` (Result: inflow bounds ± end/start padding), `core/layout/box_fragment_builder.cc:280-357` (inflow bounds with margins, negative-end clamp), `core/layout/layout_box_model_object.cc:838-859` (padding percentages against the containing block's content width); Taffy 0.13 `tree/layout.rs:331-348` (scroll_width/height), `compute/leaf.rs:19-21`, `compute/block.rs:701-707`, `compute/common/content_size.rs:16-36`.
- **Limitations:** auto end margins resolve as zero (the flex algorithm's share is not in the record); percentage trailing margins resolve against the scroller's content width like Taffy's own basis; the anchoring walk (ticket 46) needs the node-path bookkeeping this ticket added; the 175% child box cannot match Chrome exactly through the port's device-edge bounds snapping (the fixture compares the border box).
