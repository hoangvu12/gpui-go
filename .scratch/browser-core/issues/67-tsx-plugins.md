## Answer

- **Memory isolation (the ticket's decision, ADR 0003 addendum): time budget only, in process.** goja cannot cap a VM's heap; the budget bounds what a broken plugin can run, the failure paths bound what it can do, and the VM's lifetime is its slot registration (Remove drops it for the collector). A separate plugin process (real heap cap, IPC per contribution) is future work for an untrusted ecosystem — docs/adr/0003-tsx-ui-scripting.md, "Addendum: plugin memory isolation".
- **API** (all in `gpui/script`, new files plugin.go + budget.go):
  - **Slots** — the app declares a slot with the `<slot name="main" id=.../>` element (a div-like container; its JSX children are the fallback shown while no plugin fills it, like a web component's slot; `name` is a slot-only prop). `host.Slots()` returns the registry (gpui/script/host.go:233); `slots.Add(name, bundle, opts...)` registers a plugin from a compiled bundle, `slots.AddSource(name, src, opts...)` the dev shape (gpui/script/plugin.go:189, :210), `slots.Reload(name)` / `ReloadAll()` reload in place (keyed state kept, :291/:314), `slots.Remove(name)` unloads (:271), `slots.Host(name)` is read-only observability (:165).
  - **The plugin manifest** — a plugin bundle exports `plugin` instead of App: `{ slots: { main: Main } }` (readManifest, gpui/script/plugin.go:536); each component is called with `{slot}` and describes that slot's tree (describePlugin, :573; a useState write re-describes every slot root). A slot with several plugins renders them in registration order; a plugin can declare a slot another fills (nested slots).
  - **Budgets** — one goja runtime per plugin (`Slots.start` builds a Host per registration); every script turn (load, handler, timer, frame callback, promise settlement) runs under a per-call time budget (default 50 ms, zgui's number; `WithPluginBudget`, 0 disables): a watchdog arms `goja.Interrupt` — the one documented thread-safe cross-goroutine call, everything else about a VM stays on the host thread — and the InterruptedError (uncatchable in JS) fails the plugin (gpui/script/budget.go:33, :104; host.go's Load/runJS are the two budgeted seams).
  - **Grants** — `script.Grants{Actions, Shared, Network}` (nothing granted by default; `WithPluginGrants`): actions resolve through a resolver that answers only granted names against the app host's registrations (ticket 64's `WithActionResolver` seam, plugin.go:337), shared state through a gated view of the app's store that also forwards store notifications for granted keys (ticket 64's `SharedStore` seam, :353), and fetch through a prefix-gated wrapper of the app's fetcher (:417). A missing grant is a named error — `action "note.add": the plugin "clock" was not granted it` — and fails the plugin like any script error. Plugins do not inherit the app's SetGlobal values (they would bypass grants); `WithPluginGlobals` hands a trusted plugin its own.
- **Containment** — a plugin that throws, loops past its budget or renders an invalid element is left out while the app and the other plugins keep running: its slots show an error placeholder with the .tsx file and line (nodePlaceholder → placeholderElement, plugin.go:507; debug selector `plugin-error`), the failed plugin is parked (its timers, frame callbacks and in-flight work cancelled; no script runs until it reloads — host.go:248, runJS drops parked callbacks), and its handlers keep dispatching in its own runtime under its own budget even though its nodes lower with the app's tree (Node.owner, host.go:830's slot parsing, lower.go). A plugin whose module never ran (a load-time crash) fills no slot, so it is simply absent — its failure reaches the app through Add's error and `WithPluginErrorHandler`. Remove cancels the dropped VM's pending work, so nothing calls into it afterwards.
- **Dev reload** — `Host.Reload` extends to `slots.ReloadAll()` (plugin.go), so cmd/tsxdev's reload command (a .tsx change anywhere under the app's package) reloads the whole scripted surface in place; a plugin that fails to reload is contained to its placeholder while the app's reload still succeeds.
- **Types** — the generated .d.ts carries the whole plugin surface (one file, regenerated): the `slot` element with its `SlotProps` (extends HostProps with `name`), `PluginSlotProps`, `SlotComponent` and `PluginManifest` (internal/tsxgen/dts.go's elementPropTypes + pluginDTS; `GOFLAGS=-p=4 go generate ./gpui/script/types` stays clean, drift-tested both directions — tsxgen_test.go plants a removed slot element).
- **Tests** — `gpui/script/plugin_test.go` (through the public API, windowless + one windowed): two plugins in separate VMs filling the same and different slots (same state key stays two values), fallback show/replace/return, nested slots, a windowed order/click/redraw test, the budget interrupting a runaway loop (handler and load-time), a thrown error and an invalid element contained (placeholder + the app and the other plugin keep working), the grant gate denying an ungranted action and allowing a granted one (plus shared and network gates, the denied fetch rejecting with the named error), unload/reload (keyed state kept across Reload, fresh after Remove, a failed reload placeholder with recovery), dev reload through Host.Reload, plugin globals, and an unloaded plugin's timers stopping with it. The behaviour fixture: `internal/parity/fixtures/tsxslots` — the tracer's page with a slot filled by a plugin that logs through a granted action, recorded in headless Chrome (`plugin-slot`: 3 boxes, 6 events) and replayed to all three tiers (whole 0.0144 / slot ROI 0.1422, the tracer's own band) plus a wrong-plugin discrimination test and an empty-slot fallback test. A diagnostic run proved the app-side and plugin-side paths measure identically (slot ROI 0.5375 both) before the text was shortened to the tracer's "Hello!".
- **Limitations** — goja has no per-VM memory cap (the ADR's accepted trade-off: a plugin allocating within its budget grows until unloaded); the interrupt cannot break a plugin stuck inside a Go-installed function (granted sync actions count against the budget and the interrupt lands when they return); a plugin whose module never ran has no known slots, so its failure has no placeholder (it is absent — reported to the app); plugins resolve the app's registered actions only (the app's own `WithActionResolver` is its script's gate, not the plugins'); a plugin host's slots are managed by its registry (`Slots()` panics on one); plugin console output goes to stderr attributed as `[plugin "name"]`.
