## Question

How should the selected Go core, generated APIs, and native dependencies be packaged for ordinary development and distribution?

Define public versus internal boundaries, code generation ownership, prebuilt native artifact pinning and loading, ABI changes, supported architectures, toolchain requirements for users versus maintainers, dependency isolation, and error behavior when artifacts are unavailable. Keep Base as a future consumer. Account for the approved development budgets.

## Existing evidence

The [renderer contract](../../../docs/renderer-contract.md) adds a native D3D11/DirectComposition service, finite scene kernel and atlas, with embedded DXBC generated by the pinned wgsl-rs/Naga/FXC pipeline. Consumers must not run Rust, C or shader compilation. Decide native artifact grouping, feature/import/dependency manifests, ABI compatibility, source/patch/shader hashes and licensing. `repr(C)` is not the private wire schema. DLL lifetime includes retained scenes, imported/captured frames and outstanding submission/query obligations, including quarantined device-loss work. Enumerate optional Windows capabilities explicitly; the selected native backend does not imply every wgpu/custom-GPU feature combination works.

The [Windows platform contract](../../../docs/windows-platform-contract.md) adds pinned native text and AccessKit services plus narrow COM adapters behind a Go-owned Win32 host. Decide combined versus separate DLL packaging, full target dependency/features provenance, license notices, ABI negotiation and native-runtime requirements. Consumer `CGO_ENABLED=0` builds and callbacks must work with prebuilt artifacts alone. Include executable PerMonitorV2 awareness before HWND creation; a manifest copied only into a DLL is not proof that consumer applications receive it. Provider references and active native calls can outlast window closure and constrain DLL unloading.

Apply the [accepted development criteria](02-set-development-and-runtime-budgets.md): ordinary app builds must work with Go plus prebuilt native artifacts and require no local Rust or C compiler. Native compilation may be maintainer work. No hard download, disk, or timing budget has been selected.

The [layout contract](../../../docs/layout-contract.md) requires a maintainer-built version-pinned Taffy DLL and a Windows Go loader usable with `CGO_ENABLED=0`. Define ABI/version negotiation, target architecture, complete dependency/features/build provenance, artifact integrity and loading location, native runtime dependencies, missing-artifact errors, and teardown after active calls drain. A prebuilt library that still forces consumer cgo compilation does not meet the requirement. The bridge remains unimplemented; require a clean-machine consumer build and callback execution evidence before claiming this distribution path works.

## Answer

Resolved at documentation level on 2026-10-04 under the user's research-first delegation. The Go-only consumer requirement, permitted native dependencies and Windows current-PC target are explicit user preferences. Packaging and boundary details are reviewed engineering selections, not direct user quotations or authorization to implement/publish. The [distribution contract](../../../docs/distribution-contract.md) is the detailed specification of this decision.

Keep one local module `gpui-go` with future root package name `gpui`, existing independent public `authoring`, and root-level internal ABI/loader/service/Win32 adapters. Preserve public type identity and prevent package cycles. Framework generators are maintainer tools; fluent application authoring requires no generation. Public module branding and the project license remain publication work.

Package logical native services in **one exact Windows AMD64 MSVC DLL**: Taffy layout, text/rasterization, scene/D3D11/atlas/capture, AccessKit/COM and CPU image/SVG processing. Go retains the application, HWND host, entities/elements, asset sources/caches/tasks/animation and injected HTTP client. Preserve locked image 0.25.10 and resvg/usvg 0.48.1 with the full target feature graph, explicit clipboard/resource decode modes, SVG unpremultiply arithmetic and lazy font resolution through owned request/resume records. HTTP preserves default Null failure; a network client is an explicit app choice.

Embed the exact native artifact and manifest in the Windows Go package, with an explicit verified bundle directory for read-only/offline installation. Enforce module zip limits and real binary inclusion, not LFS pointers. No runtime download or compiler fallback. Use protected per-user full-hash paths, cross-process publication locking and verified open-file lifetime; Windows rename alone is not atomicity proof. Load the absolute DLL path with explicit restricted dependency search, without process-wide changes. Exact hash, machine, ABI schema/service-table and required compiled-capability checks precede service initialization; runtime OS availability remains separate.

Maintainers use static CRT (`-C target-feature=+crt-static`), unwind-enabled exports, embedded DXBC and complete build/import/feature/notice provenance. Validate actual imports and clean-machine behavior; flags alone are not evidence that redistributables are unnecessary. Consumers need Go and supplied artifacts with `CGO_ENABLED=0`, no Rust/C/resource/shader compiler. Prepare consumer executable PerMonitorV2 resources through pure-Go `.syso` tooling, with guarded early runtime setup for development and final executable inspection.

Keep successfully loaded native service code resident for the process lifetime. Logical resources still release through the accepted scope, COM and GPU completion contracts; residency does not retire quarantined submissions. This conservative policy covers providers, callbacks and capture/query obligations after the last window closes.

### Alternatives and rationale

- Separate service DLLs add version/allocator/COM combinations without providing process isolation; their license differences alone do not require separation. Reconsider grouping only with evidence of a useful distribution/build tradeoff.
- Embedded artifacts couple identity to the Go module and support offline execution. Sidecar-only distribution remains available explicitly, while first-run network fetching is not selected.
- Static libraries requiring consumer cgo, runtime native compilation and silent fallback backends fail the existing consumer or parity requirements.
- No download-size, build-speed or memory advantage was measured. Go module size limits and clean-consumer execution are delivery gates.

### Limits and remaining work

No DLL, loader, resource generator, ABI, native callback, oracle, compiler fixture or parity test was built/run. Complete source capability inventory, real loader/cache/CRT/DPI behavior, image/SVG lazy-loading and decode traces, GPU/provider shutdown and a clean Go-only consumer run remain mandatory evidence. [Documentation and snapshot checks](../../../evidence/distribution-planning-validation.json) do not establish executable correctness.

It remains open and dependent on [authoring-signature verification](10-validate-authoring-signatures.md). The policy-blocked Go upgrade was not retried or bypassed.
