# Original GPUI authoring cross-check

Research date: 2026-10-04. This is a focused primary-source check of the [counter-view proposal](../docs/counter-view-api.md), not a restart of the broad feasibility work. Findings and Go recommendations below are separate from accepted decisions.

The original repository is `zed-industries/zed`. Its live `main` resolved during this investigation to **`a84689073d296dfd39987bc7dd478e43ef76d83a`** (commit timestamp 2026-10-03T08:53:38Z). All original-source links below use that revision. **The accepted parity target remains GPUI-CE `254b5dbd47cbb5acbcc5bbdcbb322a339276c88a`.** Comparing the original does not update it. [Original comparison commit](https://github.com/zed-industries/zed/commit/a84689073d296dfd39987bc7dd478e43ef76d83a), [accepted CE revision](https://github.com/gpui-ce/gpui-ce/commit/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a).

## The original has an actual counter to compare

`crates/gpui/examples/testing.rs` contains an interactive counter and accompanying test source. It declares `Increment` and `Decrement` with `actions!`, gives `Counter` a focus handle and retained subscription, and explicitly declares `EventEmitter<CounterEvent>`. Increment changes the count and calls `notify`. Its `Render` implementation combines `key_context`, `on_action(cx.listener(...))`, `track_focus`, formatted string children, and click listeners. Startup separately installs keybindings, creates the entity through `cx.new`, and focuses it. This directly supports the broad structure of our Go draft; shortcut setup cannot disappear merely because an action handler exists. [Counter declaration and mutation](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/examples/testing.rs#L20-L58), [rendering](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/examples/testing.rs#L84-L140), [startup](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/examples/testing.rs#L185-L208).

The original example's self-subscription is a testing demonstration, not a reason for every counter to subscribe to itself. Nor does its increment method emit `CounterEvent`: our `CountChanged` payload and `Emit` call are an illustrative Go scenario, not a literal translation of that method. Tests in the original file were read, not executed.

## Render, RenderOnce, and entity identity

**Observed.** `Render::render` borrows mutable persistent state and receives `Context<Self>`. `RenderOnce::render` takes ownership of a plain component value and receives `App`. Both return an `IntoElement` value. The original documentation recommends `RenderOnce` plus `#[derive(IntoElement)]` for composing ordinary elements, reserving `Element` for manual layout and painting. [Original contracts](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L26-L31), [render signatures](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L163-L186).

Both examined revisions also expose `View`, which combines rendering with an optional backing entity identity. Blanket implementations cover a `RenderOnce` recipe with no entity ID and `Entity<T>` where `T: Render`. A custom `View` can combine parent-supplied properties with a backing entity. `ViewElement` adapts these values into the element lifecycle. This is a capability the abbreviated Go example has not yet designed explicitly. [Original View](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L181-L231), [CE View](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/view.rs#L185-L258).

The derive macro constructs `ViewElement<Self>`; the adapter stores the recipe in an `Option` and takes it when rendering. The common component path therefore consumes one recipe, rather than keeping that recipe object as the persistent application state. This does not mean a component type can appear only once or that a new recipe cannot be constructed next frame. [Original derive](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui_macros/src/derive_into_element.rs#L5-L29), [adapter storage and rendering](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L247-L269), [consumption](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L324-L350).

**Go proposal.** A single-attachment guard for mutable recipe/builders is a runtime adaptation of consuming construction. It is not an original GPUI rule saying all component references are unshareable. Entity handles refer to persistent state: the accepted CE source implements `Clone` for `Entity<T>`, and original `AnyView` is cloneable. [CE Entity clone](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/app/entity_map.rs#L511-L521), [original AnyView](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L18-L35).

Shared handles still have placement rules. Both revisions warn that views keyed by the same entity must not be siblings under the same parent: their internal element state would collide. The documented nesting case is distinct because identity is scoped by the parent path. Therefore “allow shared entity handles” must not become “any duplicate placement is safe.” The lifetime decision still needs to define Go handle ownership and the authoring decision needs identity-aware placement rules. [Original identity warning](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L192-L204), [same CE warning](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/view.rs#L196-L208).

## Child conversion and fluent authoring

**Observed.** Original `ParentElement::child` requires `impl IntoElement`; `children` requires an iterator whose item implements that trait. Conversion erases concrete element type at the composition boundary. Unsupported Rust child types fail the trait bound during compilation. String convenience comes from concrete implementations for static string slices, owned `String`, `Cow<'static, str>`, and `SharedString`; it is not arbitrary display formatting of any value. [ParentElement](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L188-L211), [string conversions](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/elements/text.rs#L304-L325), [SharedString conversion](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/elements/text.rs#L378-L384).

`Styled` requires a style accessor, supplies default methods returning `Self`, and expands method families through Rust macros during normal compilation. The original agrees with the earlier CE finding: a separate custom-author generation command is not required for these conveniences. [Original Styled](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/styled.rs#L15-L47).

**Go proposal.** The accepted `.Child("Hello")` through `Child(any)` deliberately moves unsupported-type detection to runtime. Immediate panic is a proposed way to make programmer mistakes visible while keeping the chain simple; it is not a claim about Rust's child API. Nil handling, overlapping conversion contracts, typed bulk children, and optional checked construction still need precise definitions. The implemented constructor-bound styling helper is compatible with the authoring goal, but does not reproduce Rust move checking or enforce recipe attachment.

## Low-level custom elements

**Observed.** Original `Element` associates separate `RequestLayoutState` and `PrepaintState` types. Layout produces the first; prepaint mutably receives it and produces the second; paint receives mutable references to both. Identity and source location are explicit hooks. Accessibility includes role, property writing, and synthetic children, whose method receives mutable prepaint state. The framework internally wraps concrete `E: Element` in `Drawable<E>` and ultimately erases it behind `AnyElement`. Type erasure at that boundary does not require component authors to use untyped state. [Element contract](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L53-L143), [typed Drawable](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L238-L290), [AnyElement](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L568-L606).

`SharedString` is a concrete illustration: layout state is `TextLayout`, prepaint state is unit, and later phases receive the layout state with its concrete type. The public contract also supports elements with nontrivial prepaint state. [Original text element](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/elements/text.rs#L328-L375).

**Go proposal.** Keep typed `L` and `P` in the custom-element adapter, and hide dynamic dispatch inside the framework. An explicit `CustomElement[L,P](...)` invocation is one proposed Go spelling, not something Rust authors must write. Review whether constructors can return an already adapted value before treating repeated adapter calls as an unavoidable user-facing cost. Normal view/component authors should generally use the higher-level rendering contracts. Complete identity, inspector, accessibility, and retained element-state behavior must accompany any eventual adapter specification.

## Events, listeners, and actions

**Observed.** Original `Context::listener` captures a weak entity and updates through it when invoked. `subscribe` requires the source state to implement `EventEmitter<Evt>`, and `emit` has the corresponding emitter bound before queuing an effect. Payload typing alone therefore does not express the complete emitter/event relationship. [Weak listener](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/app/context.rs#L246-L259), [subscribe constraint](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/app/context.rs#L94-L108), [emit constraint](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/app/context.rs#L760-L774).

`actions!` defines and registers unit action structs. The broader `Action` contract includes cloning, equality, names, payload construction, and optional JSON schema. Derivation supports opting out of JSON or registration; consequently a raw empty Go struct does not by itself reproduce all action services, and direct typed use must be distinguished from invocation by registered name. [Action declarations and options](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/action.rs#L11-L96), [Action trait](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/action.rs#L117-L148).

**Go proposal.** Preserve weak listener delivery and emitter/event restrictions, with explicit action registration supporting the relevant services. The technical declaration mechanism remains to be designed and compiler-validated; the original source does not settle which Go API best expresses it. A registration facility need not impose a separate application generation command.

## Differences from the accepted CE target

The overlapping Render/RenderOnce roles, View abstraction, typed element phases, fluent styles, and typed child conversion corroborate the draft. They do not make the two revisions identical:

| Checked surface | Original comparison revision | Accepted CE revision | Consequence |
|---|---|---|---|
| Hidden accessibility subtrees | No `Element::is_a11y_hidden` method in the inspected trait | Has that hook, including synthetic-node handling for hidden elements | Preserve the CE requirement in the Go design |
| Restricted child types | No `ParentElementTyped` trait in inspected `element.rs` | Provides `ParentElementTyped` with its own `Child` associated type | General `Child(any)` must not erase the ability to define restricted-parent APIs |
| View adapter implementation | Extracts layout/prepaint/paint helpers and uses the common ViewElement path | Common ViewElement path with phase logic in the implementation and hot-patching branches | This source organization difference is not evidence of a different high-level recipe contract |

Sources: [original Element and parent traits](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/element.rs#L106-L211), [CE accessibility hooks](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/element.rs#L106-L153), [CE typed parent](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/element.rs#L199-L224), [original phase helpers](https://github.com/zed-industries/zed/blob/a84689073d296dfd39987bc7dd478e43ef76d83a/crates/gpui/src/view.rs#L421-L593), [CE ViewElement](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/view.rs#L352-L535).

## What remains a human tradeoff

The source establishes consuming recipes, typed states, and compile-time child constraints in Rust. Preserve those contracts as the basis for the port proposal. How Go enforces recipe consumption and how much adapter syntax custom-element authors see need engineering proposals before asking the user to choose. Panic versus recoverable errors for unsupported dynamic children remains a direct human tradeoff under the already accepted `Child(any)` choice. Entity identity rules, event declaration mechanics, action registration, and phase capabilities need more technical design before a complete specification can be approved. None of these proposals is newly accepted by the research request.
