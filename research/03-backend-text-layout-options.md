# Backend, text and layout choices for a faithful Go GPUI port

Research date: 2026-10-04. This report revisits `evidence/earlier-research.md` under the clarified requirement: preserve GPUI's programming model, syntax where Go permits, semantics, and Base, rather than introduce another toolkit's API. It records source inspection, architectural judgments and proposed experiments. No framework implementation, rendering prototype, build comparison or benchmark was executed.

## Architectural recommendation (not accepted)

Own the GPUI-compatible runtime, element lifecycle, layout/style model, scene ordering and platform contracts. Reuse dependencies **below** those contracts. Neither Gio's widget/input model nor go-gui's retained view model should become the public model merely because its renderer is convenient. Base must exercise the same compatibility layer as application components; implementing Base on a second toolkit would leave two subtly different event, focus and layout systems.

For renderer parity, a port of GPUI's batched scene renderer over a native GPU abstraction is the strongest architectural fit. The first backend choice remains conditional: a Go WebGPU implementation minimizes non-Go build dependencies but requires a substantial correctness audit; a prebuilt wgpu-native backend reduces renderer-development risk while retaining native runtime binaries. Gio remains a candidate **window host or limited scene adapter**, not the default engine. If retaining a Rust native runtime is acceptable, evaluate an exact-version Taffy bridge; otherwise evaluate a Go port against differential fixtures. Neither choice has been accepted, and no suitable ready-made Go binding was verified. Currently inspected Go layout alternatives are not drop-in replacements.

## The renderer contract is richer than rectangles and text

GPUI's scene has separate ordered collections for shadows, quads, paths, underlines, monochrome/subpixel/polychrome sprites, surfaces, backdrop filters and filter boundaries. A primitive carries a content mask. The implementation handles surface opacity separately, replays paint operations, and keeps matched content-filter boundaries even when ordinary primitives can be clipped away. Its batch iterator and ordering rules must survive a port. Group opacity/filtering is not equivalent to multiplying each child's alpha; backdrop filtering is not equivalent to blurring a supplied image. [GPUI scene](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/scene.rs).

A backend suitability test therefore needs overlapping translucent primitives, nested clips, shadows with clipped bounds, filter groups, backdrop sampling, glyph atlas formats, imported surfaces and exact insertion order. Canvas compatibility should translate the GPUI paint primitives into this scene. A custom GPU view additionally needs a defined texture/surface import, synchronization and ownership contract; merely allowing a custom shader string is insufficient. This is an architectural requirement inferred from the inspected scene, not a claim that every GPUI platform exposes identical custom-view capabilities.

## Gio: usable seams and concrete limits

Gio's public `gpu.New(API)` returns a renderer exposing `Frame(*op.Ops, RenderTarget, viewport)`, `Clear` and `Release`. It exports API/target types for OpenGL, Direct3D 11, Metal and Vulkan. This is usable without Gio widgets, but it still consumes Gio's operation language. `NewWithDevice` takes an internal driver type and explicitly says it is for internal use; depending on that layer would mean maintaining a fork or extracting code. [Renderer](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/gpu/gpu.go), [API types](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/gpu/api.go).

The inspected public paint API has image, color, linear-gradient, paint and opacity-stack operations. Clip operations describe paths and strokes. This can represent a useful subset of GPUI painting, including nested clipped shapes and opacity, but the inspected API does not offer a public arbitrary-shader, backdrop-blur or GPUI-native-surface operation. Absence from these inspected interfaces is not proof that no extension exists anywhere; it is enough to reject an assumption of complete scene coverage. CPU-generated shadow textures or offscreen images could fill individual gaps, but change caching, quality, upload cost and compositing behavior. They require explicit parity tests. [Paint operations](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/op/paint/paint.go), [clip operations](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/op/clip/clip.go).

Text is another mismatch risk. Gio's shaper exposes glyph clusters and converts glyph sequences to outline paths or bitmap operations. That is valuable functionality but does not establish identical rasterization, subpixel atlas encoding, hinting or blending to GPUI. Text with equal Unicode content can produce different line breaks, selection geometry and pixel output when fallback fonts, metrics or rasterization change. [Gio shaper](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/text/shaper.go).

For window-only reuse, `app.CustomRenderer(true)` explicitly prevents GPU-context creation and assigns backend initialization, framebuffer swapping and frame pacing to the caller. `Window.Run` executes on the native window event-loop thread and waits. Windows publishes a `Win32ViewEvent` containing HWND. These are promising seams for a custom renderer without adopting Gio layout. However, `app.Main` normally owns the program's main thread; `app.Events` replaces it rather than exposing a universal externally pumped loop. Integrating with an existing host loop is a separate platform task. [Window options/thread entry](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/app/window.go), [application loop](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/app/app.go), [Windows handle](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/app/os_windows.go).

Gio input reuse is not a free substitution. Its frame operations register event targets; GPUI must retain its own focus, capture/bubble, key-context and action behavior. An adapter must avoid dispatching the same input through both systems and translate native composition into the GPUI input-handler contract. The inspected Windows backend distinguishes preedit from committed text, maintains composing ranges and positions candidate windows; shared IME state translates rune/UTF-8/UTF-16 indices. Those are useful pieces to reuse or study. Gio also defines semantic labels, classes and selected/enabled states, but those declarations do not prove complete OS accessibility adapters. Multiwindow creation, window destruction during callbacks, focus transfer and GPU resource sharing need a host-specific audit. [IME state](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/app/ime.go), [semantics](https://github.com/gioui/gio/blob/3397eb8f4df4d59eab121f64975173ea0d3fdb38/io/semantic/semantic.go).

## Custom renderer: distinguish three meanings of “Go GPU”

**Direct native API bindings.** Go can submit D3D/Metal/Vulkan/OpenGL commands while retaining GPUI's batching and shaders. This gives maximum control over clip masks, atlas formats, imported surfaces and blending. It also assigns device loss, swapchain resize, synchronization, command-resource retirement, shader compilation and per-platform drivers to this project. Batching should cross the foreign-function boundary per draw/command group, not per glyph or element. The public API remains GPUI-compatible regardless of how calls cross that boundary.

**Go bindings to prebuilt Rust WebGPU.** `go-webgpu/webgpu` is zero-cgo at the binding boundary, but requires wgpu-native. Its Windows loader uses `syscall.LazyDLL`; floating-point calls use goffi. This avoids requiring a C/Rust compiler for ordinary application builds when compatible binaries are supplied; it does not turn the native graphics implementation into Go. Binary selection, packaging, ABI version pinning and updates remain obligations. [Loader](https://github.com/go-webgpu/webgpu/blob/907b82e37b752ea9a2735e5beec4c9e9925f6315/wgpu/loader_windows.go), [README](https://github.com/go-webgpu/webgpu/blob/907b82e37b752ea9a2735e5beec4c9e9925f6315/README.md).

The previously inspected `oliverbestmann/webgpu` instead uses cgo/static native libraries. Its README reports more than 512 MB across all platform libraries and separates them into modules; its native package imports those modules. This is a concrete dependency-footprint warning, not the expected size of a shipped application or proof that every alternative downloads that amount. [Pinned README](https://github.com/oliverbestmann/webgpu/blob/1e5d2824fac0657917c4801ad28137e555612441/README.md), [native imports](https://github.com/oliverbestmann/webgpu/blob/1e5d2824fac0657917c4801ad28137e555612441/wgpu/wgpu.go).

**Go implementation of the WebGPU abstraction.** `gogpu/wgpu` selects independent native, Rust and browser implementations. Its default `instance_native.go` imports Go `core` and `hal`, under build constraints excluding Rust and browser builds. The Metal HAL contains Go Objective-C dispatch through goffi and loads the system Objective-C runtime. That is source evidence of a real Go abstraction/backend implementation, rather than merely renaming a Rust wrapper. It still calls OS graphics drivers. The README's broad WebGPU compliance/performance claims were not independently verified; feature presence, comprehensive correctness and production hardening are different questions. [Native entry](https://github.com/gogpu/wgpu/blob/052a7e526b23454334761537410a5e50406bdfe4/instance_native.go), [Metal FFI](https://github.com/gogpu/wgpu/blob/052a7e526b23454334761537410a5e50406bdfe4/hal/metal/objc.go).

A custom GPUI renderer can target this GPU-level API without adopting `gogpu/ui`. Switching between its Go and Rust implementations is potentially a useful differential test. Before selecting it, compile the exact GPUI shader feature set, verify texture formats and blend factors needed for subpixel sprites, check imported-surface support, and exercise error/device-loss paths. WebGPU portability does not guarantee native-surface interop or identical subpixel blending across adapters. Precompiled shaders may reduce application build work, but shader-format portability and driver compilation remain separate questions.

## go-gui: useful source, not a neutral backend package

go-gui's `RenderCmd` is a reusable flat discriminated command slice containing clip, rect, text, shadow, blur, gradient, custom shader, filter, rotation and stencil commands. This is closer to a reusable scene renderer than its high-level widget API. Yet it embeds its own `Shader`, `TextStyle`, gradient definitions and go-glyph layout pointers. It is not GPUI's scene ABI. [Commands](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/render_types.go).

The Metal backend's drawing loop takes `*gui.Window` and obtains that window's render commands; backend setup and multiwindow `RunApp` likewise depend on `gui.Window`/`gui.App`, own an event loop, and lock the OS thread. This makes direct backend reuse coupled to go-gui semantics. A cleaner option is an attributed extraction/fork of GPU/platform pieces behind GPUI-owned interfaces, after dependency and license review, rather than constructing hidden go-gui views to drive a GPUI port. [Backend lifecycle](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/metal/backend.go), [drawing dispatch](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/metal/draw.go).

Names need semantic inspection: `drawBlur` draws an expanded rounded quad through a blur pipeline; it is not by itself evidence of a GPUI-equivalent backdrop filter. `drawShadow` accounts for spread and blur expansion. `drawCustomShader` compiles application-provided Metal source and caches pipelines, but that does not define arbitrary external GPU texture ownership. Text uses a `glyph.DrawBackend` uploading textures and drawing textured quads, which is a potential lower seam but still needs atlas/raster parity analysis. [Metal draw implementation](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/metal/draw.go), [text backend](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/metal/text.go).

Platform work is valuable reference material: the tree contains IBus composition integration and a real macOS Objective-C accessibility bridge. Reusing either requires mapping GPUI element identity, selection ranges, geometry and actions into its contract, not retaining the other framework's window/view ownership. Their existence does not establish accessibility or IME parity on every platform. [IBus](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/ibus/doc.go), [macOS accessibility](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/gui/backend/metal/a11y_darwin.go).

## Text and layout choices

go-text/typesetting is a credible reusable text engine: its Go HarfBuzz shaper caches fonts and reuses buffers, and it already serves multiple Go toolkits. Preserve GPUI's text-system interface above it. A full text backend still needs font discovery/fallback, OpenType features, metrics, glyph rasterization, atlas population, color emoji and cursor/selection geometry. Native CoreText/DirectWrite adapters may better preserve target-platform behavior, at the cost of additional platform work. A pure-Go fallback is useful, but should not silently redefine text metrics. [Shaper source](https://github.com/go-text/typesetting/blob/64922d2b48df3ea2ebae4733781b7c0d0c00d91b/shaping/shaping.go), [project scope](https://github.com/go-text/typesetting/blob/64922d2b48df3ea2ebae4733781b7c0d0c00d91b/README.md).

Gio Flex is a weighted-axis layout and is unsuitable as a transparent replacement for GPUI's Taffy integration. The inspected `SCKelemen/layout` is more ambitious, with pure-Go flex/grid/block code and tests, but documents critical incompatibilities: no percentage unit, unrepresentable `flex-shrink: 0` because zero means default one, and simplified flex intrinsic sizing. Its default text measurement also counts runes, with bidi reordering absent from the layout engine. These are immediate blockers for treating it as a faithful Taffy substitute, irrespective of how many basic examples work. [Limitations](https://github.com/SCKelemen/layout/blob/6f7349411616cbb31fc83c4b5d8baf48ccccebcb/docs/limitations.md), [style types](https://github.com/SCKelemen/layout/blob/6f7349411616cbb31fc83c4b5d8baf48ccccebcb/types.go), [length model](https://github.com/SCKelemen/layout/blob/6f7349411616cbb31fc83c4b5d8baf48ccccebcb/length.go).

Legacy Yoga-derived Go flex ports are not a solution to GPUI's grid requirements and should not be assumed current. This investigation did not establish a maintained, production-ready Go binding exposing exactly the GPUI-used Taffy version. A binding is therefore a proposed integration project, not an off-the-shelf dependency claim. If a Rust native dependency is acceptable, a proposed small versioned C ABI around Taffy 0.13.0, distributed prebuilt per target, could preserve layout behavior while removing Rust compilation from ordinary application builds. This binding has not been implemented or verified. It still contains Rust and requires a native maintenance pipeline. Alternatively port Taffy's relevant algorithms to Go, preserve explicit auto/percent/length values and measurement callbacks, and differential-test against the pinned Rust version. [GPUI pins Taffy exactly to 0.13.0](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/Cargo.toml), [GPUI adapter](https://github.com/gpui-ce/gpui-ce/blob/254b5dbd47cbb5acbcc5bbdcbb322a339276c88a/crates/gpui/src/taffy.rs).

## Platform/build implications

| Route | Windows | macOS | Linux | Principal qualification |
|---|---|---|---|---|
| Gio host/renderer | D3D11/OpenGL options; default setup needs no extra dependencies | Native Cocoa/Metal; Xcode dependency | X11/Wayland native development packages | Public operations are not GPUI scene parity |
| go-gui extraction | WGL path described as cgo-free | Inspected Metal backend uses cgo/AppKit | X11/EGL path described as cgo-free | Coupled window/scene contracts must be separated |
| gogpu/wgpu default | Go HAL advertises Vulkan/DX12/GLES | Go Metal HAL inspected | Vulkan/GLES advertised | Driver/conformance claims require own qualification |
| go-webgpu native wrapper | Native DLL plus Go loader | Native library plus Go FFI | Native library plus Go FFI | Zero cgo does not mean no Rust/native binary |
| Own direct backend | Separate D3D/Vulkan work | Separate Metal/OS bridge | Separate Vulkan/GL + display-server work | Highest control and maintenance cost |

The matrix describes dependency routes, not tested support guarantees. Gio installation requirements are first-party documented; other platform breadth must be verified on real target systems. [Gio Windows](https://gioui.org/doc/install/windows), [Gio macOS](https://gioui.org/doc/install/macos), [Gio Linux](https://gioui.org/doc/install/linux), [go-gui README](https://github.com/go-gui-org/go-gui/blob/58bae296bcc1112f9e118829e25225420c6712ba/README.md), [wgpu README](https://github.com/gogpu/wgpu/blob/052a7e526b23454334761537410a5e50406bdfe4/README.md).

## Experiments to authorize later, not results

1. **Build/storage matrix:** identical GPUI/Base screen and assets; pinned Rust reference, Go renderer with Go HAL, Go wrapper with prebuilt native backend, and optional Gio scene subset. Separate network download, clean compiler build, warm no-op, one-style edit, one-runtime edit and shader edit. Measure wall time, peak memory, toolchain/module/cache/intermediate/output bytes separately. Use fresh dedicated caches, never delete the user's global caches. Hypothesis: Go application edits are faster and smaller; native modules and shader tooling may dominate cold setup.
2. **Scene parity corpus:** record identical ordered scene inputs, compare output across target GPUs at 1x/1.25x/2x DPI. Include fractional glyph positions, grayscale/subpixel/color glyphs, nested clips, transparent overlapping layers, spread shadows, backdrop/content blur, canvas paths and imported textures. Define acceptable pixel tolerances per primitive before judging results; a matching simple screenshot proves little.
3. **Layout differential corpus:** use exactly the reference Taffy version and measurement inputs. Cover percentages, indefinite sizes, min/max-content, shrink-zero, wrapping, baseline, fractional rounding, absolute offsets and grid spanning/auto-placement. Compare every node's bounds and measurement-call behavior, not only root size.
4. **Native behavior matrix:** two windows with independent scaling/focus, close during asynchronous work, clipboard/drag, IME composition/cancellation and candidate positioning, emoji/combining scripts, screen-reader tree/actions, and device loss/resize. Test Windows IMEs and accessibility, macOS input/VoiceOver, and Linux X11/Wayland separately.
5. **Runtime budget:** measure idle wakeups, CPU/GPU frame time distributions, allocations and GC work, atlas churn and upload bytes on a virtualized Base table plus rich text editor. Separate initial font/shader cache warming from steady state. No frame-rate, compilation-speedup or disk-reduction number is justified by this research alone.

Backend selection should follow these compatibility gates. For a faithful port, reducing dependency cost is worthwhile only while preserving GPUI semantics; choosing another toolkit's behavior to make a demo easy would answer a different question.
