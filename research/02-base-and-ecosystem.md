# GPUI Base, styled components, and ecosystem portability

Research date: 2026-10-04. Status: source audit and proposals; no application implementation, builds, runtime tests, or performance measurements. The project intent is a Go port preserving GPUI's programming experience and supporting corresponding component libraries. This document records evidence for that scope; proposed sequencing is not a user-approved release plan.

## Baselines and a consequential compatibility distinction

The main inspected source is `longbridge/gpui-kit` at `4c7f1350331562436df868c55ac33bebc4c6406c` (called **Kit** below). Its workspace declares version 0.7.0 and exact dependencies on `gpui-pre = 0.3.7`, platform/web/macros siblings, and related snapshot crates. These are Zed snapshots, not dependencies named GPUI-CE. A workspace comment explicitly describes a prior incompatible snapshot update and the exact-version check enforced by `script/check-gpui-pin.ts`. A Go compatibility specification should therefore identify both its core GPUI reference and its component reference. [Kit workspace](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/Cargo.toml), [pin checker](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/script/check-gpui-pin.ts).

There is also a concrete CE adaptation: `gpui-ce/gpui-component` at `c08206932417f863062d2ab70cc2854c6ca04238`. Its manifest uses `gpui-ce = 0.2.2`, `gpui_ce_platform = 0.1.0`, and renamed component packages including `gpui_ce_components_base`. This is an additional reference, not evidence that every current Kit feature works with every CE revision. [CE component workspace](https://github.com/gpui-ce/gpui-component/blob/c08206932417f863062d2ab70cc2854c6ca04238/Cargo.toml).

A bounded local comparison of the downloaded revisions found identical `popover.rs` and `virtual_list.rs`; `button.rs` differed in a test's explicit extension-trait invocation. The comparison covered three files only. It supports substantial shared implementation for these slices, but does not establish whole-library API or behavior equivalence. The compared snapshots remain under `evidence/ecosystem/` for reproduction.

## What “Base plus components” actually entails

Base owns behavior and infrastructure; the component layer supplies a styled application system. This distinction appears in implementation, not only documentation: the styled Button contains `gpui_base::Button`, forwards `Styled::style` and `InteractiveElement::interactivity`, then computes variants, sizes, icons, and theme-derived appearance around that base. [Styled Button: fields and render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/component/src/button/button.rs#L192).

Base is broader than a small set of controls. Its dependencies include text ropes, Unicode segmentation and line breaking, Markdown/HTML parsing, LSP types, and a sum tree. Component's Tree-sitter grammars are optional features. Treating all Base functionality as a mandatory first milestone could recreate considerable dependency and maintenance burden. A proposed Go package boundary should preserve access to the functionality while allowing applications to omit expensive optional subsystems. [Base manifest](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/Cargo.toml), [Component features](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/component/Cargo.toml).

“Unstyled” also does not mean zero geometry or zero theme infrastructure. Base Button supplies centering and a neutral line height, then applies caller refinements. Base has semantic tokens and infrastructure defaults; Component projects its theme into Base through `Theme::base_theme` and `Theme::sync_base`. The Go contract should distinguish behavior, control geometry, token defaults, and product styling rather than promise an entirely appearance-free implementation. [Base Button::render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/button.rs#L208), [Base Theme](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/theme.rs), [theme projection](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/component/src/theme/mod.rs#L403).

## Representative source traces and required core contracts

### Button and checkbox: a useful first compatibility slice

Base Button implements `Styled`, `ParentElement`, `InteractiveElement`, `StatefulInteractiveElement`, and `RenderOnce`. Its render tree is temporary, while `Window::use_keyed_state` preserves a focus handle under the element ID. It forwards a unified click event, exposes a semantic role and label, and refines interaction and semantic styles. A Go translation needs identity independent of builder allocation and enough shared style methods to support a custom component. [Button](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/button.rs).

Checkbox adds controlled state: unchecked, checked, and indeterminate. Activation computes the proposed next state and calls the application handler; it does not secretly replace application state. Rendering projects this state into accessibility metadata and semantic styles. Its indicator is independently composable. [CheckboxState and Checkbox](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/checkbox.rs#L17), [Checkbox::render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/checkbox.rs#L364).

Two tests expose why merely matching screenshots is insufficient: `disabled_button_is_inert_and_blocks_parent_activation` expects disabled Button to stop parent activation; `disabled_checkbox_is_inert_and_allows_pointer_events_to_bubble` deliberately expects a different policy for Checkbox. The port should copy the chosen reference's behavior per control, not install one guessed global rule. [Button test](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/button.rs#L371), [Checkbox test](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/checkbox.rs#L551).

### Popover and dialog: lifecycle, layering, and dispatch

`PopoverState::transition_to` captures previous focus, registers an open deferred context, subscribes to dismissal, restores focus conditionally, emits the open-change callback, and notifies. Its subscription captures a weak entity: the source specifically explains that a strong capture would retain the state and open-context registration after the trigger disappears. [PopoverState](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/popover.rs#L86).

`DeferredPopover` is a lifetime token backed by reference counting; the registry stores weak tokens. The test `a_state_dropped_while_open_closes_the_deferred_context` asserts prompt semantic cleanup. **Proposed Go implication:** define explicit disposal when keyed state is removed, including subscriptions and registrations. Replacing Rust ownership with Go reachability alone does not specify when an overlay stops participating in dispatch. [GlobalState token](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/global_state.rs#L11), [drop test](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/popover.rs#L389).

Popup positioning also crosses frame phases. `Popup::render` creates a canvas to capture trigger bounds during prepaint, requests another frame on first capture, then emits positioned deferred content with a priority and pointer occlusion. Popover adds action context, outside-click dismissal, and dialog semantics. A renderer abstraction that offers only “draw this finished tree” must still expose these scheduling and hit-testing capabilities. [Popup::render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/popup.rs#L130), [Popover::render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/popover.rs#L301).

Dialog composes a viewport-sized deferred host, anchored positioning, focus trap, backdrop, confirm/cancel actions, callback ordering, and topmost-only backdrop dismissal. `DialogClose` dispatches from its own focus node so it can reach its containing dialog even when another surface holds focus. Focus trapping is partly Base infrastructure: its wrapper registers a trap during `request_layout`, and Root intercepts Tab/Shift-Tab to keep traversal inside it. [Dialog::render](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dialog.rs#L525), [DialogClose](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dialog.rs#L338), [FocusTrapContainer](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/focus_trap.rs#L162), [Root tab handling](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/root.rs#L194).

### Input, textarea, and editor: one engine with increasing capability

The public input module hides its internal folder split. `InputState` aliases `InputBaseState<InputMode>`; the Input element updates presentation on an entity and returns that entity for rendering. Textarea and Editor add separate mode capabilities around the shared engine. **Proposed implication:** keep persistent editing state separate from transient input builders, and avoid accidentally making editor-only methods available on a single-line control. [Module guide](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/README.md), [Input facade](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/input/mod.rs).

The engine implements `EntityInputHandler`: text lookup, selected and marked ranges, replacing text, replacing-and-marking composition, range bounds, and point-to-character lookup. It translates UTF-16 platform ranges into its internal text offsets. `TextElement::paint` registers an `ElementInputHandler` with `Window::handle_input`, tying composition to actual painted bounds and focus. Copying keystroke handlers would miss this protocol. [EntityInputHandler implementation](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/base/state.rs#L3933), [TextElement::paint](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/base/element.rs#L2975).

Editor highlighting has an explicit replaceable interface: `InputHighlighter` receives edits and returns style runs/fold candidates; `HighlightStyleResolver` maps semantic names to colors; `SyntaxContextProvider` supports syntax-aware editing without hard-coding a parser. These are useful boundaries for optional Go parser adapters. Full fidelity still requires the surrounding selection, undo, wrapping, display mapping, diagnostics, and LSP behavior; none was executed in this audit. [Highlighting interfaces](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/editor/highlighting.rs#L13).

Native exceptions exist above GPUI's ordinary platform API: Base's macOS input helper obtains the underlying NSView and installs text-content behavior. Thus a promise that every Base capability is portable through a single generic renderer would need additional evidence. [Native input helper](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/input/base/native.rs).

### VirtualList: extension hooks must reach layout and prepaint

Base VirtualList accepts per-item sizes, stores their prefix sums, and binary-searches a visible interval with one item of overdraw. Its callback constructs visible items during **prepaint**. Each item then calls `layout_as_root` with definite space, `prepaint_at` at its scrolled origin, and later `paint`; a content mask clips the subtree. Deferred scroll requests and padding/border geometry participate. [VirtualList constructors](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/virtual_list.rs#L131), [ItemSizeLayout and visible_range](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/virtual_list.rs#L346), [prepaint](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/virtual_list.rs#L597).

This is a strong core-conformance probe. A port exposing only Render and ordinary child layout would not support this translation without new public capabilities. The source requires supplied item sizes; arbitrary unknown-height measurement, scroll anchoring after content edits, and accessibility for offscreen rows should be specified separately rather than inferred from “virtual list.”

### Dock: persistent identity and externally supplied appearance

Dock layout is a data tree with stable NodeId and PanelId; `DockArea` projects it into cached container and panel entities. `reconcile` updates surviving objects rather than rebuilding all state. `Panel` defines behavior, rendering, focus, lifecycle callbacks, and persistence; `PanelView` erases heterogeneous panel types. Renderer traits receive resolved contexts and return ordinary elements for Base to attach interaction to. [Dock architecture](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/mod.rs), [DockArea::reconcile](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/dock_area.rs#L910), [Panel and PanelView](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/panel.rs#L20).

The callback contract is unusually specific: active-state transitions are coalesced to the next tick; moving between groups calls `on_added_to` without `on_removed`; permanent removal uses `on_removed` as its deactivation signal. Persistence reconstructs panels through a registry and preserves unknown panels in tested round trips. Those semantics should be documented before a Go docking port, because callbacks can own expensive external resources. [Panel lifecycle](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/panel.rs#L46), [registry](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/registry.rs), [unknown-panel test](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/dock/dock_area.rs#L3017).

## Go fluent syntax: extensibility is the difficult part

Rust's Base `StyledExt` is blanket-implemented for every `Styled` type. It adds methods such as `h_flex`, `v_flex`, and style refinement without modifying GPUI's Div. `ElementExt` similarly adds post-layout observation to every qualifying parent element. This is how ecosystem libraries extend the familiar syntax. [StyledExt](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/styled.rs#L85), [ElementExt](https://github.com/longbridge/gpui-kit/blob/4c7f1350331562436df868c55ac33bebc4c6406c/crates/base/src/element_ext.rs).

Go methods belong to a receiver type declared in the same package. Embedding promotes methods but does not rewrite their result types: a promoted style method returning the embedded builder does not automatically return its enclosing Button. Generic methods are now described in the Go 1.27 specification; this project machine's Go 1.26.5 is a different baseline. Generic methods do not remove the same-package receiver rule. [Go method declarations](https://go.dev/ref/spec#Method_declarations), [embedded method promotion](https://go.dev/ref/spec#Struct_types).

Candidate designs, not decisions:

| Approach | Effect on the intended experience | Question requiring validation |
|---|---|---|
| Generated forwarding methods on component builders | Closest type-preserving fluent syntax | Generated API volume and build cost |
| Shared generic builder carrying component type/state | Reuses common methods while retaining component identity | Type inference, copy/alias semantics, and custom methods |
| Explicit style/behavior functions or Apply callbacks | Easy extension from external packages | Whether changed call shape is acceptable |
| One universal element builder | Broad shared syntax | Whether component-specific misuse becomes runtime-only |

A useful future syntax check is a third-party component chaining shared style, its own method, another shared style, and a typed callback. Checking only `Div().Flex().Child(...)` would leave the central ecosystem problem unanswered. No candidate was compiled or selected here.

## Capability matrix and proposed dependency order

| Probe | Core capability it exercises | Proposed evidence before declaring compatibility |
|---|---|---|
| Button + checkbox | Identity, styling, children, unified activation, accessibility | Keyboard/pointer parity; controlled state; exact disabled policies |
| Independently authored component | Public lifecycle and reusable fluent methods | No private imports; component-specific methods survive style chains |
| Popover + dialog | Deferred layout/paint, occlusion, action routing, focus, disposal | Nested overlays, outside clicks, focus return, removal while open |
| Input + textarea | Shaping, selection geometry, clipboard, IME, undo | Composition, Unicode offsets, multiline selection on target OSes |
| VirtualList | Dynamic prepaint layout, clipping, scrolling, identity | Visible ranges, variable sizes, resize, deferred scroll |
| Themed component facade | Theme context, style refinement precedence | Theme changes and instance overrides preserve behavior |
| Dock | Drag/drop, stable entities, scheduling, serialization | Move/close callback order; focus/state survival; restore |
| Editor | Shared input engine, display mapping, parser and LSP interfaces | Large-document edits, wrapped/folded geometry, composition |

Proposed order: establish element/state/style contracts; test simple controlled controls and an external component; pursue overlays, text input, and virtualization as separate deep slices; combine them into styled controls; then tackle docking and editor depth according to the eventual application's needs. Input's native protocol should be investigated early even if the full editor ships later. This is a dependency argument, not an estimate or commitment to implement all listed features first.

## One independent ecosystem check

`MeowLynxSea/yororen-ui` at `346502ac654b77fdaff3be2d7444fca8783acfc9` provides another actual CE consumer. Its core depends on `gpui-ce = 0.3`. `ButtonProps::apply` attaches behavior to caller-owned Div; alternatively, `ButtonProps::render` asks a registered `ButtonRenderer::compose` for a `Stateful<Div>`, then adds activation. The default renderer reads theme paths. [Core manifest](https://github.com/MeowLynxSea/yororen-ui/blob/346502ac654b77fdaff3be2d7444fca8783acfc9/crates/yororen-ui-core/Cargo.toml), [headless button](https://github.com/MeowLynxSea/yororen-ui/blob/346502ac654b77fdaff3be2d7444fca8783acfc9/crates/yororen-ui-core/src/headless/button.rs), [renderer contract](https://github.com/MeowLynxSea/yororen-ui/blob/346502ac654b77fdaff3be2d7444fca8783acfc9/crates/yororen-ui-core/src/renderer/button.rs).

Inference: supporting “others” means permitting external packages to create elements, attach behavior, retain focus/state, and provide themed rendering without changing core. It does not require adopting Yororen's registry or copying its API. This audit inspected one button path only; accessibility completeness and runtime maturity remain unverified.
